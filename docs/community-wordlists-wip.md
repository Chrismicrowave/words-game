# Steam 社区词表 WIP

**状态：** 社区总体方向仍为 WIP。2026-10-31 已确认全局导航/词表库 UX 与列表身份、个人纪录的数据模型方向；这些设计尚未在代码或存档中实现。早期候选方案保留在下文，仅作历史参考，与本轮确认项冲突时以本轮内容为准。
**目标方向：** 优先适配 Steam Workshop。社区功能是否随游戏首次发售上线及具体排期仍待确认。其他平台以后可各自实现社区服务，但复用同一套游戏内 UI。

最新产品决策、审核方案和实施 roadmap 汇总在
[`community-v1-discussion-summary.md`](community-v1-discussion-summary.md)。以下内容保留实现细节与历史方案；冲突时以汇总文档为准。

## 本轮已确认 UX 摘要（2026-10-31）

- 全局 **Challenges、Word Library、Community、Achievements** 是相互独立的入口。
- **Word Library** 分为互斥的 `My Lists`、`Community Downloads`、`My Published` 三组；一个列表只出现一次。收藏是跨组的独立视图/筛选，不复制列表。
- 词表库支持搜索、分组折叠、排序、收藏、语言和已游玩筛选，并记忆相关视图状态。星级排序和个人最佳用时仅用于本地个人纪录展示/排序。
- 下载的社区原版可显示远端作者信息并保持只读；玩家编辑他人内容时另存为新的自有词表，使用新 UUID、清除社区下载/发布绑定，不强制保留来源或署名。
- 公开后的可玩内容不可原地修改。标题、简介和封面等元数据可更新；词语、阶段、语言或拼音改变时必须发布为新的本地词表和新 Workshop Item。
- 词表本体、资料库/收藏状态、个人纪录和平台发布/下载绑定分开存储。具体字段及排行榜身份候选见 [词表数据模型 WIP](wordlist-data-model-wip.md)。
- 公共排行榜只考虑最多 100 个常玩词表的候选方向；Steam 是否提供可用的游玩指标、时间窗/刷新方式和历史榜单生命周期仍待技术验证，不能据此承诺上线范围。

下文较早的面板/流程/排序方案属于历史 proposal；凡与以上确认 UX 冲突的部分均已 superseded，但保留文本以供追溯。

## 已确认目标

- 玩家可以在游戏内浏览其他玩家上传的词表。
- 玩家可以上传自己的词表。
- 社区评价帮助好内容排到前面。
- 优先适配 Steam Workshop；未来其他平台的社区后端是独立工作，不在本次 Steam 功能中做双后端/跨平台同步。社区功能是否随游戏首次发售上线及排期仍待确认。
- 保留本地词表玩法；社区不可用不应阻止玩家游玩本地词表。

## 当前边界与非目标

- 本 WIP 不决定 leaderboard 后端，也不等同于旧计划里“把 Supabase leaderboard 换成 Steam leaderboard”。Top 100 只作为公开榜资格候选；指标与平台可行性见[数据模型 WIP](wordlist-data-model-wip.md)。
- 本阶段不构建跨平台统一社区数据库；优先适配 Steam Workshop。
- 投票数/排名不代表内容安全或质量已获认证；内容解析仍须由游戏做本地 schema 与内容校验。
- 本文不决定点赞/踩、排序权重、自动更新、举报门槛、词表挑战计分或成就条件。

## 参与者与主要任务

| 参与者 | 主要任务 |
|---|---|
| 浏览玩家 | 找到合适词表、预览内容、评价、下载/订阅，并明确选择是否开始游玩。 |
| 上传玩家 | 从自己的本地词表上传，并看到创建、上传、协议、失败和重试状态。 |
| 词表作者 | 管理自己的上传；可更新标题、简介和封面等元数据，确认发布/审核结果。玩法内容变化时发布新词表和新 Workshop Item。 |
| Steam 服务 | 返回可见条目、用户投票状态、订阅/下载进度和上传回调。 |

## 历史候选面板结构（superseded where conflicting；保留供参考）

```text
社区词表
┌ 浏览 ───────── 已订阅 ───────── 我的上传 ┐
│ 搜索…   排序：热门 / 好评 / 最新   语言筛选 │
│ [词表卡片] 标题 · 作者 · 语言 · 阶段数       │
│            评价 · 订阅/本地状态               │
│            预览    订阅/下载    评价           │
└──────────────────────────────────────────────┘
```

建议的卡片内容：标题、作者、语言/混合标记、阶段数、简介、评价/订阅数和当前状态。详情视图可预览阶段样本，提供完整内容校验结果和显式“开始游玩”动作。

候选分区：

- **浏览：** 搜索、排序（热门/好评/最新）、语言筛选和分页；冷启动时如何排序仍待定。
- **已订阅：** 订阅列表、缓存/更新状态、取消订阅；离线时展示可用本地内容。
- **我的上传：** 创建/上传状态、作者自己的条目、更新同一条目和失败重试。

上述标签、卡片字段、排序名和动作位置都是讨论稿。

## 历史玩家流程草案（superseded where conflicting；保留供参考）

### 浏览与使用

1. 打开社区词表，选择排序/筛选或搜索。
2. 打开详情并预览内容、语言和阶段数量。
3. 选择评价；确认已提交，或在失败时恢复旧状态并提示重试。
4. 订阅/下载，等待 Steam 的下载完成回调后再读取安装目录。
5. 通过内容 schema、大小、词条数、字符串长度和实际语言内容检查。
6. 玩家显式选择“开始游玩”。下载完成不自动启动词表。

**待确认：** 下载与订阅是否合并成一个按钮；是否另提供一次性下载；社区列表能否不订阅直接预览；断网时已下载内容保留多久。

### 上传与作者更新

1. 从“我的词表”选一个列表，预览将上传的标题、说明、语言、词条数和可见性。
2. 上传前做本地结构/大小/内容校验，显示明确状态。
3. 首次创建只在用户确认后执行一次 `CreateItem`；遇到结果超时/未知时先查询或恢复状态，避免盲目重试并创建重复条目。
4. 若 Steam 要求接受 Workshop Legal Agreement，显示待协议状态和后续动作。
5. 条目创建成功后保存 Workshop 条目 ID；元数据更新沿用该条目，玩法内容变化则创建新列表和新条目。

**待确认：** 作者署名/标题/说明规则；能否基于他人词表修改并重新公开；更新对已订阅用户何时生效；更新前版本和本地纪录如何关联。

### 下载副本与身份

- Workshop `PublishedFileId` 是远端条目身份；项目现有自定义列表 UUID（`// u:...`）是本地可编辑词表身份，两者不可混用。
- 建议订阅/下载源在本地按 Workshop ID 只读使用，不让现有编辑/保存流程覆写 Workshop 安装目录。
- 若玩家选择编辑/另存，创建独立的本地副本和新 UUID，保留来源条目/作者/版本元数据；原订阅源保持只读。
- 游戏记录、挑战进度和未来排行榜是否跟随远端条目 ID、内容版本或另存副本 UUID，需要先定身份规则。

## 必须先补证或修复的项目耦合

- 当前本地列表支持结构化中文/混合词条和显式拼音；社区 JSON schema 必须保留结构化字段，不能只传扁平 `.txt`。请在实现前核对 [`WordListData`/providers](../Assets/-Scripts/WordList) 的真实序列化字段。
- 先前静态调查发现 Duplicate/Export 路径对结构化内容可能有损；上传和另存应依赖修复/验证同一底层导出路径，不能从损坏的导出实现开始叠加。
- `SaveCurrentList`、TXT 导入、provider 加载和列表编辑是不同写入入口。Community provider 的只读保护需覆盖所有写入口；不能只在社区 UI 隐藏“保存”按钮。
- 语言标签可能不准确；中文玩法开关不能只信元数据，必须按解析后的实际词条内容作校验，不得通过加载后删条目再保存的方式“过滤”。
- 下载内容为不可信输入。反序列化前/后均需限定文件大小、schema 版本、词条数、字段长度、允许的字符与段类型，拒绝路径穿越/异常结构；不得把内容当代码执行。

以上是实现前置核对项；本轮未修复或完整追踪这些代码路径。

## 技术建议（不是最终平台抽象决定）

### 客户端边界

```text
CommunityPanel / community view-model
              ↓
       ICommunityListService
              ↓
       SteamWorkshopAdapter  → ISteamUGC
```

- UI 只依赖社区词表查询、详情、订阅/下载、投票和上传状态接口；Steamworks 逻辑集中在 adapter。以后其他平台可实现自己的 service，复用 UI，但不在本阶段接入。
- 用不透明的社区条目 ID 表示远端身份；Steam adapter 内映射到 `PublishedFileId`。不要把本地 UUID、显示名称或列表文件路径用作远端键。
- 上传/更新保留结构化 schema 版本；下载后做实际内容语言校验，再交给现有 provider 读取。Steam 查询元数据可放语言、schema 版本等筛选字段，但不能替代内容验证。
- Steam Workshop 已有投票、按总票/趋势/发布时间排序的查询能力。MVP 建议先使用 Workshop 原生排序，不自建“推荐”得分；结果和投票列表可能用缓存，UI应允许刷新，不能承诺票数立即改变名次。
- 离线或 Steam API 不可用时显示局部状态，保留本地列表入口；不能假装投票/上传已成功，也不能阻止本地游戏。

### Workshop 身份和许可

- `CreateItem` 首次创建成功后保存其远端 item ID；后续仅元数据更新沿用同一 ID。词语、阶段、语言、拼音或规则内容变化必须创建新列表和新 item。
- 上传者必须有允许上传的实际应用许可；Steam 官方指出 Family Sharing 等临时许可不能上传。
- 预览图需要设置 Steam Cloud 配额，并在后台启用 `ISteamUGC` 文件传输；这些配置要通过 Steamworks Publish 发布。
- 私有测试：建私有 Steam Community group，在 Workshop 可见性选择 `Developers & Testers` 并填写 group ID；用有 App 许可的 A/B 测试账号完成上传、浏览、订阅、下载和投票。确认测试条目可见性包括 B，避免单条 item 隐私设置使其不可见。
- 在收到下载完成回调并取得 install path 前，不读取 Workshop 文件；取消订阅不等于立刻删除本地数据，按 Steam API 状态处理。

## 实施前小型技术验证

在完成动作 UX 决策后，再用两名有许可的测试用户验证完整流程：

1. 私有 Developers & Testers 组和私有 beta 分支配置完成。
2. A 从结构化本地列表创建一个条目，确认 API Name/metadata、内容 schema 和协议状态。
3. B 查到条目、预览、订阅；等待下载完成回调后读取并校验，随后显式开始游玩。
4. B 提交评价，回读自己的投票；模拟 API 失败时界面回滚或刷新，不伪显示成功。
5. A 更新原条目元数据；B 验证显示变化与成绩作用域不变。随后 A 以同一内容创建新版本，B 验证它成为独立条目和独立成绩作用域。
6. 测试取消订阅、离线、坏 JSON、超大文件、结构化混合/中文词条、上传超时未知结果和重试；确保不覆盖本地源文件、不重复创建条目。
